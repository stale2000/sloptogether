## Configuration

1. Deploy the web app with the workspace lockfile and root install context. Set `PUBLIC_APP_URL=https://www.clips.gg/sloptogether` and the server secrets from `.env.example` in the child deployment only.
2. Apply the repository migrations to new environments in order. The live Clips.gg project has a later migration history than this checkout: Supabase reports existing Bits prompt-lock and stream-reservation migrations, and its schema already has the action kind, proposal, election and stream columns. Reconcile migration history before applying migration 023; do not replay an equivalent production migration. Migrations 020–022 are documented as applied to the `sloptogether` schema; pre-air upscale defaults off and is enabled on the `stale2000` test channel, where one manually reviewed HLS test passed. Previously built hosted workers are unsupported for new capabilities until rebuilt and qualified. Set the role password through a secret manager and use that login for the app and worker. For Vercel, use the Supabase IPv4 transaction pooler with username `sloptogether_app.<project-ref>`; the direct database hostname is IPv6-only and is not resolvable from the Vercel runtime. Set `SLOPTOGETHER_DATABASE_SSL_CA` to Supabase's public `prod-ca-2021.crt` and retain certificate verification. Do not use a shared Clips.gg application role or a database superuser for the public runtime. Set `SLOPTOGETHER_USE_CLIPSGG_DATABASE=true` only for that configured shared-project connection. The server checks both the pooler host and the schema-scoped username.
   Supabase currently reports RLS disabled on the 44 SlopTogether tables. The `sloptogether` schema has no `USAGE` grant for `anon` or `authenticated`, so those API roles cannot reach the tables through those grants. Keep it private; verify actual exposed-schema configuration before any API exposure. Do not grant public schema access or enable RLS alone; first define the intended role policies, or RLS will deny the runtime's queries.
3. The private `sloptogether-media` bucket and `sloptogether-upload-gateway` Worker are deployed. The Worker is bound only to that bucket; `uploads.clips.gg` is its Cloudflare-managed custom domain, and its `workers.dev` address and the bucket's public `r2.dev` domain are disabled. Gateway/ticket secrets, `R2_ACCOUNT_ID`, `R2_BUCKET_NAME`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` are configured in Vercel Production; health reports `objectStorageMode=cloudflare_r2`. The R2 API token is restricted to `sloptogether-media`; do not reuse the Clips.gg media bucket or credentials. This health check proves configuration presence only. A real base generation has passed input read, upload and publication; repeat private object, signed PUT, ticket, range and publication checks after relevant changes. Deploy and supervise `npm run media-worker` with the schema-scoped database login, R2 and moderation credentials. Keep CORS limited to `https://www.clips.gg` and allow only the exact R2/gateway upload hosts in workers.

The production panel asset loads, but the current Twitch version is not Hosted Test or Released.

   Bits prompt queueing is implemented behind SLOPTOGETHER_BITS_PROMPT_QUEUE_ENABLED, SLOPTOGETHER_BITS_POLICY_APPROVED, and SLOPTOGETHER_BITS_EVENTSUB_READY; all remain false until the Extension is released, a fixed catalog SKU exists, and the transaction subscription is verified. Configure SLOPTOGETHER_BITS_PROMPT_QUEUE_PRODUCTS_JSON to match the actual Twitch catalog SKU and amount. The panel displays Twitch's exact Bits count, screens the viewer's prompt before purchase, and makes it eligible in the normal vote only after authoritative transaction verification. This buys one queue entry; it does not guarantee selection or generation. Twitch's official Queue+, BitPoll and View Message Alert examples document Bits queues with customizable fields, Bits-created polls and viewer messages, respectively. These are precedents for custom fields in fixed app-defined interactions, not blanket approval for every AI-generation feature. Follow the normal Extension review process and never call Bits a donation or promise a USD price. Configure a paid Comfy Cloud API key as `SLOPTOGETHER_COMFY_API_KEY`, the moderation key from step 5, separate gates `SLOPTOGETHER_COMFY_FRAME_GENERATION_ENABLED=true` and `SLOPTOGETHER_COMFY_PROMPT_GENERATION_ENABLED=true`, and a comma-separated `SLOPTOGETHER_COMFY_FRAME_GENERATION_CHANNEL_IDS` allowlist. The start-frame workflow uses the open-weight Z-Image-Turbo template at 8 steps and exactly 448×256, then saves that image directly. It has no partner-image node charge; Comfy Cloud bills active GPU runtime at its current rate, so cost varies with cold-start and execution time. The service allows one active or uncertain job per shared account, caps it at five requests per hour and each operator at three per hour, screens the brief before submission, validates and screens generated H3 prompts before filling the proposal, and screens generated images before attaching them to the normal proposal form. Ambiguous provider submissions are marked uncertain and are never automatically retried; the uncertain row blocks further Comfy jobs for the shared key until an operator resolves it using the Comfy Cloud account UI or support. Frame prompts and provider job IDs expire after seven days through the supervised media worker's outbox cleanup, so keep that worker running. Keep the key out of the browser, media worker and Windows executable.
